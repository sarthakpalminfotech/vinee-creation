# Vinee Creation — Business spec (authority: audit brief §2)

Vinee Creation is a textile **trader**: orders grey fabric from weavers, has it dyed/finished at mills, folds it, sells it to customers. Everything is counted in **taka** (roll) and **meters** (2 decimals).

## Rules (IDs are used in AUDIT.md and code comments)

**Masters** — R-M-1 party group → parties (POs go to the group, goods come from a party). R-M-2 quality has an *original name* (weaver documents) and a *nickname* (mills, customers: challans, programs, order screens). **There is no item master and there are no item codes; colours belong to qualities.** R-M-3 mills, with an optional **GSTIN**. R-M-4 branches (racks are retired). R-M-5 a **common colour library** (shade name = the identifier, optional description, a colour picker and/or a photo); a quality links colours from it and may have colours **of its own** (private, never in the library); a colour can be inactive per quality; every quality colour shows when it was last used in a program / an order. Shade charts are gone from the UI (a hidden `__library__` chart satisfies the old NOT NULL columns). R-M-6 customers, with an optional **GSTIN**. GSTIN is saved trimmed in capitals; one that does not match the 15-character pattern only shows an amber warning.
**Grey PO** — R-PO-1 party group, quality, ordered meters, rate, PO number typed from the paper PO. R-PO-2 ordered/received/pending + status **Open / Partly received / Received / Closed (short)**. R-PO-3 partial receipts from any party of the group. R-PO-4 *Short received* = ordered − received (m and %). It is a PO figure only and is not part of the shrinkage report.
**Receiving grey** — R-GR-1 party, weaver challan no + date, destination godown (a **branch**) or direct to a mill. R-GR-2 many takas, meters ≤ 2 decimals, fast grid, unique taka no within the challan. R-GR-3 updates the PO. R-GR-4 direct receipts go straight to *grey at mill*.
**Racks (retired)** — R-LOC-1..3 are retired: no rack assignment, no rack filter, no picking list. Branches stay. The `locations` table, `takas.location_id` and old `taka_moves` history are kept (read-only data); new takas get no rack.
**Send to mill** — R-SM-1 a mill challan is **always issued against weaver (grey) challans**: pick the weaver challan (party auto-filled), then some or all of *its* takas that are still in the godown. R-SM-2 several weaver challans travel together as **one main challan (e.g. 121) with one sub-challan per weaver challan (121A, 121B, …)**; the main number starts at 1 (editable, unique), letters continue A…Z, AA, AB…. R-SM-3 PDF: a cover page (sub-challan table) + one page per sub-challan, quality always by **nickname**; a single sub-challan can be printed alone. R-SM-4 takas leave the godown and become grey at the mill. R-SM-5 no double send; every save is one transaction. R-SM-6 a main can receive more weaver challans while OPEN (a weaver challan that already has a sub extends it); CLOSED refuses additions; reopening is allowed. Older challans without a main show as "Old challan DC-0001".
**Program (rewritten in client changes 3)** — R-PG-1 a program belongs to **one mill** and is issued **against weaver challans**: it can hold several qualities and several weaver challans; takas come only from grey at that mill (`MILL_GREY`, `mill_id` = the program's mill), whether sent with our mill challan or delivered direct to the mill. R-PG-2 **the user chooses the exact takas** (no first-in-first-out, no "takas in this program" check field) and gives them a **colour of the taka's quality** (linked and active); within one weaver challan different takas can get different colours; takas without a colour stay grey at the mill. A program line = one weaver challan + one colour (`program_lines.receipt_id`, `quality_id`). R-PG-3 while a program is not Done more takas can be added (a challan + colour that already has a line extends it); old programs (auto-picked, no weaver challan) stay readable and receivable. R-PG-4 program PDF (quality by **nickname**): grouped quality → weaver challan → colour (swatch **or photo** printed), takas and meters, taka lists in column blocks, totals per colour and a grand total. `programs.quality_id` only keeps the quality of the first line: a line's quality is always `COALESCE(pl.quality_id, pr.quality_id)`.
**Mill receipt (rewritten in client changes 3)** — R-FR-1 a mill return challan belongs to one program and can cover several weaver challans and colours; partial receipts any number of times. R-FR-2 every received taka needs its **finished meters** (shortage = grey − finished, unchanged; the grey meter is the weaver-challan meter). R-FR-3 **one lot number per program line** (program + weaver challan + colour): required when any taka of that line is received, set by the first receipt (`program_lines.lot_no`), later receipts show it locked and the repo rejects a different value; the same lot text may appear on different lines. The lot is also kept on each taka (`takas.lot_no`) so folding, inventory, damage details, job work, sales and availability can show it. R-FR-4 received takas become finished goods; pending is counted per line and per colour; the program is Done after the last receipt.
**Folding** — R-FD-1 enter real folded meters; opening a mill challan **preselects all its pending takas**, saving asks for confirmation. R-FD-2 folding shortage = finished − folded. R-FD-3 sellable meters (folded − damaged) are the stock/sales meters. **R-FD-4 damage:** each row can be marked with damaged meters (≤ folded, ≤ 2 decimals), an optional photo, optional voice note (record up to 2 min or attach) and notes; saved in the same transaction as the folding. Damage is separate from the folding shortage; a damaged taka is still one taka; sellable meters feed inventory, availability, dead stock and order allocation. Damage cannot be edited after folding is saved.
**Shrinkage report (shortage)** — R-SH-1 per-taka chain grey → finished → folded; shortage only **at the mill** and **at folding**; percentages against grey. R-SH-2 direct-to-mill takas use the same chain. R-SH-3 summaries by PO, party, quality, mill, program, with a separate Damage column (also per taka). Nothing is measured between the weaver and the mill. All user-visible "loss" wording is "shortage".
**Inventory** — grey at our place (by branch) · grey at mill · in dyeing · finished goods; filters quality/party group/party (+ mill, branch, colour, Damaged); counts and meters (finished meters are sellable meters); the four views add up to all active takas.
**Availability** — R-SO-1 for a quality (nickname) and each of its colours: finished, in dyeing (program/mill), grey at mill, grey at our place by branch, plus a block **"Open POs: N · Pending: X m"** (POs of that quality that are Open or Partly received).
**UI rules (client changes 3)** — **R-UI-1 taka display:** the meters are what matter. Everywhere takas are listed use `TakaChip` / `TakaGrid` (tap tiles: meters large and semibold, the taka no small and muted `#12` top-left, optional tiny badges, ≥ 44 px, equal widths: 3 columns phone, 4 tablet portrait, 6 landscape/laptop) or `TakaList` (read-only column blocks: each block its own bordered box with its own header, a gap between blocks, number muted left / meters right in a fixed column, zebra rows, a footer per block, a grand total; a fixed 4 blocks per A4 page in PDFs). Tables keep the same emphasis (muted number, dominant meters). **R-UI-2 tablet first:** iPad/tablet (portrait and landscape) and laptop are the main devices, phones must not break. No sideways page scroll at any width (wide tables scroll inside their own card); breakpoints `md` 768 tablet portrait, `lg` 1024 landscape / small laptop, `xl` 1280 laptop; two-column layouts (form + summary) start at `lg`, below that the summary is a sticky bottom bar; touch targets ≥ 44 px; inputs use 16 px text (no iPad zoom); modals fit the screen height with internal scroll; long names truncate; no hover-only actions.
**General** — R-G-1 clean responsive UI. R-G-2 lists have search/filter/pagination/loading/empty/error states. R-G-3 inline validation, no double submit. R-G-4 exact 2-dp meters. R-G-5 every multi-row change is one transaction. R-G-6 taka state machine with full history; invalid transitions rejected by the code, not just hidden in the UI.

## Taka state machine (enforced in `src/db/repo.js`, logged in `taka_moves`)
`GODOWN_GREY` → (rack assign/move stays in state) → `MILL_GREY` (send to mill) → `IN_DYEING` (program) → `FINISHED` (mill receipt) → `FOLDED` → `SOLD` (order allocation).
Direct receipts start at `MILL_GREY`. Each transition requires the exact previous state and aborts the whole transaction otherwise.

**Client changes 2 additions.** New statuses `JOB_WORK`, `NOT_RETURNED`, `WITHDRAWN`, `GREY_SOLD`. Allowed new transitions (anything else is rejected, see `TRANSITIONS` in repo.js): `FOLDED→JOB_WORK`, `JOB_WORK→FOLDED` (received), `JOB_WORK→NOT_RETURNED` (closed short), `NOT_RETURNED→JOB_WORK` (reopened), `FOLDED→WITHDRAWN`, `GODOWN_GREY→WITHDRAWN`, `WITHDRAWN→<previous status>` (cancel), `GODOWN_GREY→GREY_SOLD`. `INACTIVE_STATUSES` (`SOLD, GREY_SOLD, WITHDRAWN, NOT_RETURNED`) are not stock: reconciliation = godown + mill + dyeing + finished + job work = all active takas.

## Rules added in client changes 2
- **R-JW-1** Only plain (never job-worked) FOLDED takas go to job work; damaged takas go with their sellable meters.
- **R-JW-2** The system picks the takas, oldest folded first then taka id: whole takas until the taka count and the meters are both reached; only the last taka may overshoot. Not enough stock rejects the line (and the whole save).
- **R-JW-3** One transaction creates challan `JW-n` (integer, decided inside the save) and moves the takas to `JOB_WORK`.
- **R-JW-4** Receiving (any number of partial receipts, each one transaction): taka returns to FOLDED, same quality + colour, marked job-worked (`jw_type` = job type or "Job work"), sellable meters = received meters (cannot exceed the sent meters). Job work shortage = sent − received, reported separately (shrinkage report), never part of mill/folding shortage.
- **R-JW-5** Challan status: OPEN → PARTIAL → COMPLETED (automatic); CLOSED (short) needs a reason and turns pending takas into NOT_RETURNED; reopen restores JOB_WORK. A closed or completed challan takes no receipts.
- **R-JW-6** Job-worked stock is shown separately from plain stock everywhere finished goods appear (inventory cards/detail filter, availability panel); a job-worked taka cannot be sent to job work again.
- **R-SO-3** A job-work order (`orders.job_work=1`, optional `job_type`, `job_notes`) allocates only job-worked takas (job type must match, case-insensitive, when the order names one); a normal order allocates only plain takas. Linking a challan to an order is information only (no reservation); only open job-work orders can be linked; "job work required" cannot be turned off while challans are linked.
- **R-WD-1** Withdraw "Others" needs a reason; FG takes plain or job-worked FOLDED takas (toggle per line, default plain), grey takes GODOWN_GREY takas. Numbering `WD-n` is shared. Each taka's previous status is stored.
- **R-WD-2** Cancel puts every taka back to its exact previous status in one transaction; the withdrawal stays on record as Cancelled and can be cancelled once.
- **R-GS-1** Grey direct sell: one party (weaver), takas must be GODOWN_GREY of that party (and of the chosen weaver challans when given), a customer is required, rate optional (amount = rate × meters). One transaction creates `GS-n` and moves the takas to GREY_SOLD.
- **R-INV** Inventory has a fifth stage "FG in job work", a Withdraw chooser, "Sell history" (Done orders + grey sales, newest first, totals) and "Withdrawals" modes.

## Decisions taken by the audit (change by editing the named place)
- **D-1 Decimals:** columns stay `REAL` (no destructive retype). Every meter is validated to ≤2 dp and rounded on write; all SQL sums use `ROUND(…,2)`, JS sums use integer hundredths. Meters never exceed a few thousand per row so no drift is possible at 2 dp.
- **D-2 No server:** the app is client-only; `repo.js` is the enforcement layer, wrapped in `tx()` (`src/db/client.js`; SQL transaction on sql.js and Turso).
- **D-3 Shortage chain (changed in client changes 1):** grey (weaver challan) → finished (mill return challan) → folded. The weaver step and the weaver→mill step are no longer measured. Percentages are against grey.
- **D-4 Closing a PO short** freezes further receipts; "Re-open PO" reverses it. A *Received* (fully delivered) PO still accepts more meters (over-delivery shows as negative shortage).
- **D-5 Duplicates:** taka numbers unique per challan (DB unique index + code). PO number unique. Masters: case-insensitive duplicate names/racks/shade numbers rejected.
- **D-6 Racks retired:** grey is tracked by branch only; old rack data and history stay in the database.
- **D-7 Program allocation** takes takas first-in-first-out from grey at that mill for the chosen quality (one quality per program).
- **D-8 Customer orders:** the existing "allocate → SOLD" button is kept as generated; availability checking does not depend on it (Q6).
- **D-9 Demo data** is only written into a completely empty *local* database, never a remote one unless `VITE_ALLOW_DEMO_SEED=true`; "Reset demo data" is disabled on remote databases.

- **D-10 Turso stays browser-direct (known risk):** the browser talks to Turso with the token in the build; the client accepts this for now (see AUDIT.md). No server, no login.
- **D-11 No auto-wipe:** the local "auto-repair" that deleted all data on duplicate PO numbers/nicknames is removed; duplicates only produce a console warning.
- **D-12 Voice notes:** uploaded to Cloudinary (resource_type auto) when configured; otherwise, or if the upload fails, kept only on the recording device (IndexedDB, keyed by the damage id, `voice_local = 1`). Audio is never stored in the main database.
- **D-13 Old challans:** mill challans without a main stay readable as "Old challan DC-0001" (`/dispatch/old/:id`); they are not rewritten. `/dispatch/:id` is the main id; if no main has that id the old challan with that id opens.
- **D-14 Schema version:** start-up skips all schema work when `settings.schema_version` equals the code's version; bump `SCHEMA_VERSION` for every schema change.
- **D-16 (client changes 2)** The system picks takas for FG withdrawals/job work; the user previews and confirms (the save repeats the pick inside its transaction).
- **D-17** Job-worked stock is kept separate from plain stock (plain orders never use it, job-work orders never use plain).
- **D-18** Linking a challan to an order is information only; only open job-work orders can be linked.
- **D-19** Received meters of a job-work taka may not exceed the sent meters. Sell-history date of an order = date of its last allocation (fallback: order date). Sell-history amount is shown only where a rate is known (grey sales).
- **D-20 (client changes 3)** `programs.quality_id` stays NOT NULL and holds the quality of the first line; never read it as "the quality of the program" (use `COALESCE(pl.quality_id, pr.quality_id)`; the list shows all qualities).
- **D-21** Lot numbers are locked per program line after the first receipt (exact text; the repo rejects a different one). The old row-only `createFinishedReceipt` and the old `createProgram` (auto-picking) signatures stay only for tests and scripts; the UI never uses them. Old programs are received with one lot per line too.
- **D-22** Changing the mill on step 1 of a new program clears the chosen takas. A weaver challan cannot be open in two cards: choosing it again re-opens its card.
- **D-15 Colour list for programs/orders:** active colours only; a colour already on an order stays allowed when that order is edited.

## Rules added in client changes 4
- **R-SO-4 — Sell to order.** Finished goods can be given to an open customer order from Inventory → Withdraw → Finished goods → *Sell to order* (`/inventory/withdraw/fg-order[?order=id]`). It is the same business action as *Auto-allocate*: folded takas → `SOLD` with `order_id`, a `taka_moves` row (ref `ORDER`) each, the order becomes Done when every line is covered (so it appears in Sell history). Per line the user may change the takas / meters to give (prefilled with the pending amounts) or set it to 0; the system picks the oldest eligible takas (plain stock for a normal order, job-worked stock of the named type for a job-work order; whole takas, the last may overshoot the meters, sellable meters). Not enough stock → the line stays pending and the user may still confirm what is available. Core: `previewOrderAllocation(orderId, wants)` (read-only) and `allocateOrderLines(orderId, wants)` (one transaction); `allocateOrder(id)` = the core with the full pending amounts.
- **R-SO-5 — Available stock on the order detail.** Per line: ready (folded) plain and job-worked (the eligible kind highlighted), finished-still-to-fold, in dyeing (program, mill, lots), at job worker (JW challan); once per quality: grey at mill (by mill), grey at our place (by branch), open POs. Each line shows *Short by X takas / Y m* or *Covered* from the eligible ready stock against the pending quantity. Buttons: *Allocate now* (opens R-SO-4 with the order preselected) and the existing *Auto-allocate*. Repo: `orderAvailability(orderId)`.
- **R-FR (updated) — Receive from the mill in 3 steps + confirm.** 1 mill challan (no, date, notes, photo) → 2 weaver-challan cards: pending takas by shade, a lot no per shade (locked once the line has one), no meters → 3 finished meters, one collapsible card per lot no (lines that share a lot text share a card; one open at a time; Enter = next, a lot's last Enter opens the next lot; Paste = one value per line, the count must match) → confirm modal → one transaction (`createFinishedReceipt`, unchanged). Finished meters: > 0, at most 2 decimals; an amber note when finished > grey. Leaving with unsaved entries asks first.
- **R-FD-5 — Folding → In mill.** `/folding/in-mill` lists every program with takas still in dyeing, grouped by mill (program no, date, qualities, colour chips, issued / received / pending takas + meters, days since issue); search + mill filter. A program opens *Receive from mill* in a restricted mode (`/folding/in-mill/:id/receive`): only the receive steps, no program actions; Back and save return to In mill; after a save *Fold these takas now* opens Folding on that mill return challan (`/folding?open=<receipt id>`). **This is not security** — the app has no logins yet.
- **R-UI-3 — Full-width desktop.** From 1280 px up pages use the full content width, capped at 1800 px (`.page-w*` classes in `index.css`); below 1280 px the tablet layouts are unchanged. Forms: 3 fields per row at `xl`, 4 at `2xl`; form + summary pages keep a fixed 340 px sticky summary column; taka grids 8 columns at `xl`, 10 at `2xl` (tiles keep their size); card lists 3–4 per row; the order detail has two columns at `xl`.

### Decisions (round 4)
- **D-23** Auto-allocate and Sell to order share one allocation core (`planOrderAllocation`); the Auto-allocate result and tests are unchanged. Giving more than a line's pending amount is rejected; giving to a Done order through *Sell to order* is rejected.
- **D-24** Lot cards in step 3 merge lines whose lot text is identical (exact text after trimming). The lot itself is still stored per program line.
- **D-25** The In mill "restricted mode" is a simplified screen, not an access rule (see open questions).
- **D-26** `availabilityDetail` crashed when any finished taka carried a lot number (lots were grouped from takas instead of [taka, meters] pairs); fixed while building R-SO-5.

### Open questions (round 4)
- **Roles / login:** who may receive from the mill — today anyone can; "In mill" is only a simplified screen.
- Whether finished meters may ever be entered *later* than the receipt (today they are required at receipt time).
